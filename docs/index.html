1 Reproducible Analytical Pipelines (RAP)

RAP

It is important for analysis to be reproducible. Different analysts using the same methods with the same data should get the same results.

RAP is a way of using software engineering techniques to improve the reproducibility of your analysis. By minimising manual steps, using version control , and producing good documentation analysis can be higher quality, reproducible, reusable and more efficient.

In 2022 the Government Analysis Function published it’s RAP Strategy. This set out it’s vision for more efficient and high quality analysis, using RAP to achieve this.

Applying RAP principles helps you comply with the requirements in the AQUA book for good quality assurance, and was recommended in the Goldacre Review into using health data for research and analysis.

The key advantages of RAP are:

  • Higher quality analysis and reduced risk, with quality assurance built into all parts of the process

  • More efficient and reliable processes

  • Improved transparency and greater confidence in the analysis from producers, managers, and users

  • Improved business continuity and knowledge management

  • Analysis that is easier to adapt and reuse

In a RAP your code, data, and configuration are separated. This allows you to: apply code to updated data sets without needing to alter it; easily update model parameters without code changes; selectively publish code without exposing sensitive data or model parameters.

In DHSC we have a variety of tools to help develop and implement RAPs into your work. This book aims to familiarise yourself these tools and fundamentals of RAP.

Not all RAPs will include all of the below, but we should aspire to meet as much as possible and appropriate. We will cover the majority of the above in this book.

RAP is a code agnostic approach, however this book will focus on RAP using R. The principles are transferable to other languages, but the specifics may not be.

1.1 What makes a good RAP?

Code

The best way to incorporate RAP into your work is using code, and in particular open source languages such as R or Python.

  • Your code will use an appropriate coding standard to ensure readability, i.e. the Tidy style guide.

  • Your code will require minimal manual intervention to produce it’s outputs.

  • Your code will be modular and repeated processes written as functions

  • Your code will be well structured and organised into appropriate folders.

  • Your code will have undergone the appropriate level of quality assurance (QA).

  • Your code will be well documented, including a readme document and function.

  • Your code will include unit testing.

  • Your code will be fully packaged for easy distribution.

Data / Pipeline

Analysis can use data from a variety of sources, and in a variety of formats. For your RAP the data needs to come from a relatively stable source, so as not to need rewriting at every use.

  • Your data will be handled in a tidy format.

  • Your data will come from a managed source, such as a database.

  • Your pipeline will use continuous integration or continuous deployment and run tests.

Documentation

To be understood and maintained by future users (including yourself!) your RAP needs to be well documented. This will help with any issues running the pipeline, both with the code and any methodology. Documentation is also an important part of keeping a clear audit trail for your analysis, this is particularity vital for anything business critical.

  • Your code will produce informative and useful logging (for troubleshooting, and ensuring your RAP has run correctly.

  • Your code will be version controlled using Git.

  • You will produce clear documentation for future users, such as READMEs.

  • Your code will be published in the open.

  • Any changes to your RAP will be clearly documented and signposted, i.e. in a change log.

Aspects like packaging, continuous integration, and unit testing may not be appropriate for smaller project. Similarly, it will not always be possible to publish code in the open. However all projects should be properly documented, version controlled, and adhere to coding standards.
